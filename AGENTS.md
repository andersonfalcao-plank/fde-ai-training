# fde-ai-training

A Next.js 16 app (App Router, React 19, TypeScript) styled with Tailwind CSS v4 and shadcn/ui components. Managed with pnpm.

## Commands

| Command             | What it does                                   |
| ------------------- | ---------------------------------------------- |
| `pnpm dev`          | Start the dev server                           |
| `pnpm build`        | Production build                               |
| `pnpm start`        | Serve the production build                     |
| `pnpm lint`         | ESLint                                         |
| `pnpm format`       | Format all files with Prettier                 |
| `pnpm format:check` | Fail if any file is not Prettier-formatted     |
| `pnpm typecheck`    | Generate Next types, then `tsc --noEmit`       |
| `pnpm test`         | Run Vitest once (`pnpm test:watch` to watch)   |
| `pnpm check`        | lint + format:check + typecheck + test + build |

Run `pnpm check` before every commit. CI runs the same steps as separate Lint, Typecheck, Test and Build checks on pull requests to `main` and on pushes to `main`; Lint and Test must pass before a PR can merge.

Tests live next to the code they cover as `*.test.ts(x)` and use Vitest with React Testing Library. Run one file with `pnpm test src/components/navbar.test.tsx`, or one test with `pnpm test -t "links Home"`.

Add shadcn components with `pnpm dlx shadcn@latest add <name>`, then `pnpm format`.

## Conventions

Every change must follow these.

### Where files go

- `src/app/` — routes only: `page.tsx`, `layout.tsx`, `loading.tsx`, `error.tsx`, `route.ts`. Co-locate route-private pieces in `_components/` inside the route folder.
- `src/components/ui/` — shadcn primitives. Generated by the shadcn CLI; edit sparingly.
- `src/components/` — shared app components built from those primitives.
- `src/lib/` — non-UI code: utilities, data access, server helpers.
- `public/` — static assets served as-is.
- Import with the `@/` alias (`@/components/ui/button`), not long relative paths.

### Server Components by default

A Server Component renders on the server and sends no JavaScript to the browser. Every component is one unless it opts out.

- Add `"use client"` only when the component needs state, effects, event handlers, or browser APIs.
- Push `"use client"` down to the smallest leaf that needs it; keep pages and layouts as Server Components.
- Fetch data in Server Components, not in client effects.
- Pass only serializable props from a Server Component to a Client Component.

### One module reads `process.env`

`src/lib/env.ts` is the only file that reads `process.env`. It validates every variable when first imported and exports a typed `env` object; everything else imports from `@/lib/env`.

- Never read `process.env` anywhere else.
- `env.ts` is marked `server-only`: importing it from a Client Component fails the build. Read values in a Server Component and pass them down as props.
- When you add a variable, add it to `env.ts` and to `.env.example`.
